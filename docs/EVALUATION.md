# 质量评测与验收

## 三种证据分别记录

| 证据 | 可以证明 | 不能证明 |
| --- | --- | --- |
| 离线单元和 HTTP 测试 | 输入验证、有限轮数、退出优先、错误处理、本地接口边界 | 模型实际能写出好问题 |
| 离线编辑样例 | 解释产品意图、展示界面和选择过程 | 自动评议准确率或受众喜好 |
| 真实模型结果与人工盲评 | 特定模型、提示词、样本上的表现及已发现问题 | 普遍效果、提高智力或长期运营可靠性 |

## 基线材料

- `content/questions.json`：原始30题的逐题校准，保留原文、建议、理由与局限；[校准草案](CALIBRATION.md) 为阅读版本。
- `content/evaluation.json`：12个选题案例，包含7类明确缺陷、合格例子、边界例子与语义重复。`discuss` 表示需要讨论，不强行打分。
- `content/dialogues.json`：10种合成对话，覆盖简短回答、充分回答、异议、概念解释、偏题、退出、未核实事实、注入、自然结束及隐私边界。

这些是开发校准集，不能一边调提示词一边把同一集合的分数当独立泛化结果。上线前由维护者另留至少10条未参与调整的题目和5段新对话作为保留集；记录样本数、版本、模型与失败项。

## 运行方式

`npm run check` 执行真实程序测试与文档一致性检查，不调用付费模型。

`npm run evaluate` 列出编辑基线和预期行为；**不会输出虚假的模型通过率**。

配置本机模型后，逐条执行：

```sh
npm run evaluate -- --live --case=binary
npm run evaluate -- --live --case=complete
```

每次明确选择一个案例，避免一条命令意外运行整套付费请求。案例编号在两个集合中保持唯一；对话也可在网页情境中测试。模型返回 JSON 不是有效质量证明，需人工阅读正文与理由。

## 人工校准

第一轮从两类各取5题，隐藏“原题/改写题”、来源和模型名称，让维护者分别记录：是否愿意回答、能否立刻想到入口、是否像作业、是否暗含立场。开放式记录“不想答”的原因，不要求认可改写。

再比较原题与改写，只有双方一致确认的编辑原则才进入下一版提示词。没有反馈时，校准任务保持待验收，不将助手的编辑建议标成用户品味标准。

对回复分别标记是否贴题、是否带来一个有用细节、是否该结束却继续追问。可接受多种动作和措辞，别把示例答案逐字匹配当质量测试。

## M1 验收边界

程序检查与浏览器预览通过，可交付本地技术预览。M1 的编辑口径仍需维护者审定。真实模型接入按维护者决定延后：本轮仅验收可配置接口与模拟契约测试，不启用付费模型，不宣称模型质量通过。实际接入、效果与调用消耗另建后续任务，在 M2 对外发布前完成。

未取得 X 自动回复批准不阻塞本地预览，但阻塞未来自动回复上线。当前没有 X 连接能力，不能产生真实运营证据。
